# 04. Данные и расчёты

Как организованы данные платформы и какие правила нельзя нарушать. Здесь описана **целевая модель**; что из неё уже
в миграциях, показано в таблице раздела 1.

## 1. Схемы PostgreSQL

Одна база, одна схема на домен (ADR-0002), миграции goose, типизированный доступ через sqlc. Домены не импортируют
друг друга и не пишут в чужие схемы; `dashboard`, `reports`, `recommendations` читают чужие схемы только на чтение
(ADR-0012).

| Схема | Назначение | Состояние |
|---|---|---|
| `tenants` | организации, участники, приглашения, API-ключи | ✅ |
| `projects` | проекты, функциональные единицы SCI, политики | ✅ окружения, теги, правила атрибуции — позже |
| `cloudaccounts` | подключения, запуски синхронизации, результат сверки | ✅ |
| `usage` | FOCUS-записи, партиции по месяцам | ✅ |
| `carbon` | расчёты, интенсивность сети | ✅ |
| `finops` | бюджеты, индекс цен регионов | ✅ |
| `recommendations` | рекомендации, их статус, измеренный результат | ✅ |
| `automation` | планы изменений | ✅ исполнения и dry-run — фаза 3 |
| `reports` | отчёты | ✅ расписания — позже |
| `notifications` | получатели, outbox доставок | ✅ |
| `settings` | значения платформы и организаций, история | ✅ |
| `platform` | операторы, журнал доступа оператора, группы ошибок | ✅ |
| `audit` | журнал действий | ✅ |
| `licensing` | подписки и планы (ADR-0022) | 🗓️ следующая |
| `inventory`, `kubernetes`, `cicd` | ресурсы, кластеры, пайплайны | 🗓️ фазы 2–3 |

Названия `identity`, `access`, `integrations`, `cloud`, `cost`, `sci`, `optimization`, `observability`, `billing`
из первоначального наброска **не заводим**: они дублируют существующие схемы. Соответствие: `tenants` ≈ identity+access,
`cloudaccounts` ≈ integrations+cloud, `usage`+`finops` ≈ cost, `carbon` включает SCI, `recommendations` ≈ optimization.
Дробить имеет смысл, когда схема реально разрастётся.

## 2. Мультитенантность

- Каждая клиентская таблица содержит `tenant_id`; запрос идёт только в `database.WithTenantTx`, который выставляет
  контекст через `SET LOCAL`.
- Изоляция на трёх уровнях: тенант берётся из проверенной identity (не из тела запроса), RBAC на каждом
  обработчике, RLS в PostgreSQL с `FORCE ROW LEVEL SECURITY`.
- Приложение подключается ролью без суперпользователя и без `BYPASSRLS`; миграции — другой ролью.
- Фоновые задачи несут `tenant_id` и работают в том же контексте.
- Тест изоляции: попытка прочитать чужой объект по UUID, через экспорт и фоновую задачу должна давать 404.

## 3. Стоимость

- Источник: AWS Cost Explorer или FOCUS-экспорт, GCP BigQuery export → нормализация в **FOCUS v1.4**.
- Хранится исходная валюта и сумма; суммы — `numeric`, не `float`; `NaN`/`Inf` и неверный код валюты отвергаются
  до записи.
- Импорт идемпотентен (upsert по ключу строки): повтор не удваивает расходы. Поздние корректировки перезаписывают
  период, а не добавляются.
- Отсутствующая стоимость — это отсутствие, не ноль.

### Качество данных (сверка с облаком)

После каждой синхронизации сохранённые дневные суммы сверяются с суммами самого облака (сначала AWS Cost Explorer).
Расхождение сверх допуска возвращает курсор синхронизации назад, чтобы следующий запуск перечитал эти дни.
Результат хранится на запуске и на подключении (миграция `0017`), показывается в интерфейсе и порождает событие
`connection.data_quality`. Проверяются: сумма, пропущенные дни, свежесть. Если облако не даёт контрольной суммы,
статус «не проверено» с причиной, не «ок».

## 4. Углерод

- Энергия × интенсивность сети (location-based); SCI считается только если клиент сообщил функциональные единицы,
  иначе `null`, не оценка.
- Методика версионируется и неизменяема: сейчас `RLX-PROVISIONAL-1` (статус provisional, происхождение коэффициентов
  указано). Новый набор — новая версия; старые результаты не переписываются.
- Каждый результат хранит `methodology_version`; в ответе API вместе с цифрами идёт методика и оговорки
  (embodied carbon не включён).
- Измерение и оценка различаются; единицы явные (kWh, gCO₂e/kWh, kgCO₂e).
- Нет «универсальной формулы»: измеренное, смоделированное по использованию и распределённое по стоимости — разные
  методы с документированными ограничениями.

Ещё не сделано: хранение снимка входных данных расчёта, воспроизводимый пересчёт и сравнение версий, market-based
расчёт, embodied emissions (SCI-компонент M), водопотребление (нужны отдельные источники и модели).

## 5. Рекомендации и эффект

Жизненный цикл: `open → approved → applied → verified` или `dismissed` (ADR-0013, ADR-0025). Прогноз экономии лежит
на самой рекомендации; **измеренный результат** — отдельная запись `impact_verifications`: среднее за 14 дней до
изменения против 14 дней после (3 дня задержки биллинга пропущены), в масштабе 30 дней, стоимость и углерод отдельно.
Меньше 10 дней данных — число не считается (`inconclusive`), ничего не экстраполируется. Метод не контролирует
изменение нагрузки; это записано в самом результате. В отчётах и интерфейсе прогноз всегда подписан как прогноз.

## 6. Автоматизация

Платформа ничего не исполняет (ADR-0017). План содержит анализ риска, шаги и откат, утверждается человеком отдельной
ролью. Исполнители (Terraform, Kubernetes) — фаза 3, за отдельными учётными данными, с dry-run, идемпотентным ключом
и блокировкой от конкурентного запуска. Универсального «авто-отката» не обещаем: он реализуется на тип операции.

## 7. Общие правила таблиц

| Правило | Решение |
|---|---|
| Ключи | UUID |
| Время | `timestamptz`, UTC |
| Деньги | `numeric`, валюта рядом |
| JSONB | для изменяемых атрибутов, не вместо реляционной модели |
| Идемпотентность | уникальные ключи импорта, `unique`-задачи очереди |
| Версионирование | методика, настройки (история), политики |
| Аудит | append-only с точки зрения приложения |
| Секреты | не в БД и не во фронтенде (ADR-0010); адреса получателей шифруются `secretbox` |
| Партиционирование | `usage_records` по месяцам; новые крупные таблицы — сразу |
| Удаление | soft delete только там, где его требует бизнес-логика |

## 8. Производительность и хранение

Дашборд читает из read-моделей, а не считает всё при каждом открытии (ADR-0012). По росту: суточные и месячные
агрегаты, партиционирование, при реальной необходимости — вынос временных рядов Kubernetes в специализированное
хранилище, а в PostgreSQL остаются метаданные и агрегаты. Нужна политика хранения, экспорт и удаление данных
организации, проверяемое восстановление из резервной копии (PITR) и документированные RPO/RTO — **пока не описаны**,
см. [очередь работ](06-gap-analysis.md).
