# 05. Стек и внешние сервисы

Принцип: бизнес-логика, расчёты и изоляция данных остаются в нашем коде; внешние сервисы подключаются там, где
экономят время без потери контроля. Источник истины для каждой функции назначен заранее.

## Выбранный стек

| Задача | Выбор | Основание |
|---|---|---|
| Backend | Go, модульный монолит, chi (ADR-0001, 0007) | один деплой, границы доменов в коде |
| База | PostgreSQL 18, RLS | основное хранилище, изоляция тенантов (ADR-0011) |
| Миграции / доступ к БД | goose / sqlc + pgx | типизированный SQL |
| Очередь | Redis + Asynq (ADR-0003) | синки, расчёты, отчёты, доставка уведомлений |
| Аутентификация | Auth0, управляемый OIDC (ADR-0004) | SSO, MFA, сессии без собственного хранения паролей |
| Frontend | Next.js 16, React 19, TypeScript, Tailwind (ADR-0006) | клиентская и операторская панели |
| Контракт API | OpenAPI; тест сверяет с маршрутами | типы фронтенда генерируются |
| Объектное хранилище | S3-совместимое (MinIO локально) | отчёты, сырой биллинг |
| Секреты | не храним; шифрование получателей `secretbox`; Vault/KMS перед хранением клиентских ключей | ADR-0010 |
| Наблюдаемость | OpenTelemetry, Prometheus, Grafana, Tempo, Loki, Sentry | |
| Ошибки сервисов | таблица `platform.error_groups`, консоль оператора (ADR-0021) | |
| CI | GitHub Actions, сканирование безопасности | |
| Платежи | Stripe позже, за интерфейсом провайдера (ADR-0022) | |

## Что не подключаем и почему

| Инструмент | Решение | Когда пересмотреть |
|---|---|---|
| **Supabase** | не нужен | нужна своя логика расчётов и интеграций в Go; БД — обычный PostgreSQL, аутентификация — Auth0, хранилище — S3, realtime — polling/SSE. Supabase даёт то, что у нас уже закрыто, и добавляет второй источник правды по авторизации |
| Keycloak | не нужен сейчас | если потребуется самостоятельное размещение IdP (требование клиента); тогда замена за OIDC-интерфейсом |
| Kafka / шина событий | нет (ADR-0003) | измеренная нагрузка и независимые команды (триггеры ADR-0005) |
| Temporal | нет | появятся длительные многошаговые процессы с ожиданиями (исполнители автоматизации) |
| Несколько провайдеров аутентификации | нет | усложняет безопасность |
| Микросервисы | нет | один из трёх триггеров ADR-0005, с отдельным ADR |
| ClickHouse / Mimir | нет | метрики Kubernetes вырастут за пределы агрегатов в PostgreSQL |
| Свой платёжный контур | никогда | карты обрабатывает провайдер |

## Что подключить дальше

| Когда | Что |
|---|---|
| До хранения реальных клиентских учётных данных | Vault или секретное хранилище облака |
| Перед приглашениями по e-mail и расписанием отчётов | транзакционный e-mail провайдер |
| Перед коммерческим запуском | платёжный провайдер за интерфейсом (ADR-0022) |
| Когда появятся тарифные ограничения и поэтапный выпуск | флаги функций (уже есть через движок настроек), Unleash — только если не хватит |

## Отличия от первоначального наброска

| В наброске | В проекте | Причина |
|---|---|---|
| Keycloak или managed OIDC | Auth0 | ADR-0004 |
| Маршруты `/app` и `/platform` | клиентские маршруты в корне, консоль оператора `/operator` | Next.js route groups, ADR-0020 |
| 20 PostgreSQL-схем | схема на текущий домен | не создавать пустые схемы заранее |
| Роли «Platform Owner / Admin / Support / Billing / Auditor» | оператор `viewer` и `admin` | достаточно на старте; расширять по мере появления сотрудников |
| Роли клиента «Workspace Admin, DevOps, FinOps, Auditor» | `owner`, `admin`, `engineer`, `billing`, `viewer` | сопоставимо; матрица прав редактируемая — в планах |
| Workspaces внутри организации | организация → проекты | отдельный уровень workspace пока не нужен |
| Outbox/inbox и версии событий между модулями | outbox только для уведомлений | нет шины; внутренние события — цепочка задач Asynq |
