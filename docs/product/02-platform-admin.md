# 02. Админка платформы (консоль оператора)

Отдельный контур для владельца SaaS и уполномоченной команды Reliabilix. Это **не копия клиентского дашборда**:
клиент управляет своей инфраструктурой, оператор — самим сервисом.

Реализация: маршрут `/operator` во фронтенде, `/api/v1/operator/*` в API, отдельная роль PostgreSQL, таблицы
`platform.operators` и `platform.operator_access_log` (ADR-0020). Роли оператора: `viewer` (чтение) и `admin`
(разрешённые действия). Клиентская роль `owner`/`admin` **не даёт** доступа к консоли, и наоборот: оператор не
получает клиентские данные автоматически — доступ к чужим данным идёт через отдельные функции, которые пишут в
журнал доступа и в аудит организации.

## Принципы

1. Консоль видит **метаданные**, а не содержимое клиента (счета, ресурсы, секреты).
2. Каждое чтение и действие оператора логируется: кто, когда, какой организации, что сделал.
3. Администратор платформы не равен владельцу организации. Минимум привилегий: `viewer` по умолчанию.
4. Показатели берутся из реальной телеметрии (БД, очередь, метрики), не из декоративных графиков.
5. Секреты в интерфейсе не показываются никогда, только статус «настроено / не настроено».

## Разделы

Статусы: ✅ есть · 🟡 частично · 🗓️ нет.

| Раздел | Что должно быть | Статус |

| Overview | организации, активные, неуспешные синки, очередь, доставка уведомлений | 🟡 организации, доставка, нездоровые подключения, состояние системы |
| Organizations | список, владелец, тариф, число участников, подключения, статус, дата | 🟡 список и метаданные; детали и смена состояния — позже |
| Users & Access | пользователи платформы, внутренние роли, приглашения, проверка прав | 🗓️ операторы заведены в БД, UI управления нет |
| Plans & Billing | тарифы, подписки, счета, платежи | 🗓️ ADR-0022 принят, реализация следующая; платёжный провайдер — позже |
| Usage & Quotas | потребление и лимиты по организациям | 🟡 порт `entitlements`, лимиты настраиваются через настройки; отчёта потребления нет |
| Integrations Registry | реализованные коннекторы, версии, статус, ограничения | 🟡 версии в `VERSIONS.md`, статус интеграций в `operator/system`; экрана реестра нет |
| Carbon Data & Models | версии методики, коэффициенты, источники, качество | 🟡 методика версионируется в коде, импорт датасета — фаза 2 |
| Jobs & Scheduler | очереди, неуспешные задачи, повторы | 🗓️ состояние очереди в метриках; экрана нет |
| System Health | API, БД, Redis, хранилище, workers, внешние зависимости | 🟡 `operator/system`, `/readyz`, `admin doctor`; метрики — в Grafana |
| Feature Flags | флаги, доступность по тарифу, переопределение на организацию | ✅ через движок настроек (module switches, locks), ADR-0023 |
| Audit & Security | аудит, события аутентификации, смена прав, доступ поддержки | 🟡 аудит организации и журнал оператора есть, сводной страницы нет |
| Support & Incidents | обращения, инциденты, диагностика клиента | 🟡 журнал ошибок сервисов (ADR-0021); обращений нет |
| Platform Settings | глобальные настройки, обслуживание, закрытие регистрации | ✅ движок настроек, режим обслуживания и ворота регистрации |

## Что намеренно не делаем

- Не обрабатываем банковские карты. Платёжный провайдер хранит реквизиты, платформа — только идентификаторы и статусы.
- Не строим helpdesk: сначала лёгкий журнал обращений и инцидентов, ссылки на job id и ошибки синхронизации.
- Не заменяем observability-стек: здоровье берётся из health checks и Prometheus/Grafana.

## Следующие шаги

1. Страница организации (участники, подключения, лимиты, последние ошибки, смена тарифа с обязательной причиной).
2. Экран тарифов и подписок после реализации модуля `licensing` (ADR-0022).
3. Экран очередей и неуспешных задач: повтор только идемпотентных задач, причина сбоя.
4. Временный, обоснованный и аудируемый доступ поддержки к данным организации (срок, область, явное завершение).
