# Security model (baseline: OWASP ASVS 5.0)

- **AuthN**: Auth0 (OIDC, MFA there). The API verifies RS256 JWTs itself: cached JWKS with rotation handling, `iss`, `aud`, `exp`, `nbf`; `none`/HS256 rejected. The dev verifier exists only when `ENV=dev`. Machine access: API keys (`grk_`), stored as SHA-256 only, shown once, revocable, role `ci` (may call only `/ci/evaluate`; machines have no access to automation).
- **Tenancy and roles from the database, not the token**: membership is resolved through a SECURITY DEFINER lookup; removing a member or changing a role applies immediately. Self-service onboarding and invitation acceptance are the only routes that run without a tenant; an invitation is one-time, expires in 7 days and is bound to a verified email address.
- **AuthZ**: RBAC per route (`auth.Require(permission)`), server-side only. Last-owner protection and "only owners touch owners" are domain rules with tests. Machines can never approve recommendations.
- **Tenant isolation**: tenant from the verified identity -> repository argument -> `app.tenant_id` -> PostgreSQL RLS (`FORCE ROW LEVEL SECURITY` on every tenant table, enforced by an integration test). Missing context returns zero rows. Object keys are tenant-prefixed and built by `storage.Key` (path traversal rejected).
- **DB roles**: `greenops_api` (reads usage/carbon, never writes them) and `greenops_worker` own nothing and have no BYPASSRLS; audit is INSERT/SELECT only. Cross-tenant needs (membership lookup, API-key lookup, job fan-out) are a handful of `SECURITY DEFINER` functions owned by a NOLOGIN BYPASSRLS role; EXECUTE is granted per role and tested.
- **HTTP**: timeouts, 1 MiB body cap, strict JSON decoding, RFC 9457 errors without internals, security headers, per-IP rate limit (in-process; move to Redis for several replicas), exact-match CORS, request ids, no header/body logging.
- **Cloud access**: customer-created read-only IAM role + per-connection ExternalId (confused-deputy protection); `credential_ref` is a reference and key-like values are rejected. The platform stores no customer secrets.
- **Reports/exports**: files in S3-compatible storage under `tenants/{id}/`; downloads are tenant-checked through RLS; CSV neutralizes formula injection.
- **Audit**: written in the same transaction as the change (login-adjacent events, onboarding, invitations, role changes, removals, API keys, cloud connections and syncs, recommendation decisions, reports, budgets, policy changes). `GET /audit-log` for owners/admins; the Overview shows an allow-list of user-facing actions only.
- **Automation** (ADR-0017): the platform plans but never executes. A job needs an approved recommendation, a still-valid residency check and a second human approval (`automation:approve`: owner and engineer; never admin, viewer, billing or machine keys). Plans are built only from identifiers validated against strict patterns (they contain shell commands people will copy), carry a rollback plan and a risk level, and `Job.CanExecute` demands approval plus rollback. One live job per recommendation; no DELETE grants.
- **GCP** (ADR-0018): the platform's own service account reads only the customer's billing export table. A dataset label carrying the connection's unguessable token must exist before any query (confused-deputy protection, re-checked on every sync); identifiers are validated and quoted only after validation, values are query parameters; every query has a byte cap and a row cap. Customer-fixable failures are reported specifically and never retried.
- **Azure** (ADR-0041): the platform's own multi-tenant Entra application reads only the customer's Cost Management export container, with the role the customer assigned (Storage Blob Data Reader on that container). Container metadata carrying the connection's unguessable token must exist before any read (confused-deputy protection, re-checked on every sync); tenant, account, container and directory are validated by strict patterns, the storage host is built from the validated account name and redirects are never followed; only the connection's subscription is read; file count and bytes are bounded. No key, SAS token or secret of the customer is accepted or stored.
- **Cloud billing exports** (ADR-0016): export locations are validated (API and DB constraints), the role gets `s3:GetObject` below the export prefix only, manifests may not point outside the export folder, and files are streamed with size and cardinality limits.
- **Notifications** (ADR-0019): destination addresses and webhook URLs are sealed with AES-256-GCM (key from the environment, context-bound to tenant and row) and never returned; webhook signing secrets are derived, not stored; webhook/Slack calls are https-only, refuse private/loopback/link-local/metadata addresses at connect time (DNS rebinding safe), never follow redirects and never put the URL in an error; e-mail goes only to tenant members with header-injection-safe messages; delivery state lives in RLS-protected tables with split API/worker privileges; destination changes and terminal failures are audited without the address.
- **Operator console** (ADR-0020): operators are rows only the migration owner can write; cross-tenant reads are SECURITY DEFINER functions returning metadata only (no payloads, addresses, tokens or customer data) and executable by the api role only; every console request is written to an append-only access log before data is returned, actions are also recorded in the affected tenant's audit log; non-operators get 403/404, API keys never qualify.
- **Error log** (ADR-0021): messages are sanitized before storage (credentials, tokens, query strings, e-mail addresses removed), recording is bounded and never blocks or fails a request, only the operator functions can read it.
- **Settings** (ADR-0023): the catalog bounds and validates every value; organizations can change only tenant-scope settings, and never one an operator fixed for them (service check plus restrictive RLS policies); operator writes are admin-only SECURITY DEFINER functions with history and tenant audit records; secrets are never settings; a failing store means defaults, never an open door (limits default to the configured value, gates fail closed only for explicit maintenance mode). Retention floors (operator log 90 days, deliveries and errors 7 days) are enforced in the database.
- **Licensing** (ADR-0022, design): entitlements are checked server-side in the owning domain before a resource is created; the client's plan and limits are readable by its members, changeable only by operators or the billing provider's webhook.
- **Supply chain / CI**: govulncheck, golangci-lint (gosec + module-isolation rules), gitleaks, trivy, semgrep, distroless nonroot images, read-only containers with dropped capabilities.
- **Observability**: request ids, structured logs without PII payloads, Prometheus business metrics, optional OTLP traces, Sentry (no PII by default).
